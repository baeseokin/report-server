## 1. 보안

### 1-1. 🔴 Git에 커밋된 비밀키 폐기·재발급
- **현황:** `data/tmp/` 아래 Kubernetes Secret 파일 3개(`booking-db-secret.yaml`, `booking-secrets.yaml`, `booking-sendon-secret.patch.json`)가 2026-11-09 커밋(`da77556`)에 포함되어 GitHub `origin/main`에 push 되어 있습니다. 실제 값으로 보이는 **Sendon(알림톡) API 키, 관리자 토큰, OTP 시크릿, DB 접속 정보**가 들어 있습니다. 파일 첫 줄에는 "excluded from Git"이라고 적혀 있지만 실제로는 제외되지 않았습니다.
- **위험:** 저장소가 공개 상태이거나 접근자가 늘어나면 알림톡 무단 발송(비용 발생), 예매 시스템 관리자 권한 탈취로 이어질 수 있습니다.
- **조치:**
  1. Sendon API 키, `ADMIN_TOKEN`, `OTP_SECRET`, DB 비밀번호를 **즉시 재발급·변경**합니다. (이력 삭제보다 먼저 해야 합니다.)
  2. `.gitignore`에 `data/tmp/`, `*secret*.yaml`, `*.patch.json`을 추가하고 `git rm --cached`로 추적을 해제합니다.
  3. `git filter-repo` 등으로 이력에서 제거한 뒤 force push 합니다.
  4. 이 파일들은 ticket-booking 프로젝트용이므로 해당 저장소나 별도 비밀 저장소로 옮깁니다.

### 1-2. 🔴 Git에 포함된 DB 백업 덤프 제거
- **현황:** `data/*.sql.gz`, `data/approval_line_*.sql` 등 6개 덤프 파일이 Git에 추적되고 있습니다. 성도 이름·연락처·계좌번호·비밀번호 해시가 들어 있을 수 있습니다.
- **조치:** `.gitignore`에 `data/*.sql*`을 추가하고 이력에서 제거합니다. 백업은 접근이 통제된 외부 저장소(NAS, 암호화된 클라우드 스토리지)에 보관합니다.

### 1-3. 🟠 세션 저장소 전환 및 시크릿 강제
- **현황:** `express-session` 기본 메모리 저장소(MemoryStore)를 쓰고 있습니다. 서버가 재시작·재배포되면 모든 사용자가 로그아웃되고, API 서버를 2대 이상으로 늘릴 수 없습니다(현재 replica 1). `SESSION_SECRET`이 없으면 `"secret-key"`로 동작합니다.
- **조치:** `express-mysql-session`(기존 MariaDB 사용) 또는 Redis 저장소로 바꿉니다. 운영 환경에서 `SESSION_SECRET`이 없으면 서버가 시작되지 않도록 합니다.

### 1-4. 🟠 로그인 보호 및 비밀번호 정책
- **현황:** 로그인 시도 횟수 제한이 없습니다. 신규 계정과 초기화 계정의 비밀번호가 모두 `0000`입니다.
- **조치:**
  - `express-rate-limit` 등으로 계정·IP별 로그인 실패 횟수를 제한합니다(예: 5회 실패 시 10분 잠금).
  - 초기 비밀번호를 임의 값으로 만들어 알림톡으로 보내거나, `require_password_change`를 확실히 적용해 첫 로그인 때 변경하지 않으면 다른 기능을 쓸 수 없게 합니다.
  - `helmet`으로 보안 헤더를 추가합니다.

### 1-5. 🟠 비로그인 공개 API 점검
- **현황:** `/api/public/users`, `/api/public/roles`는 로그인 없이 부서·역할별 사용자 ID와 이름을 돌려줍니다. 로그인 ID를 추측하는 데 쓰일 수 있습니다.
- **조치:** 어디에서 쓰는지 확인한 뒤 로그인 필수로 바꾸거나 응답 항목을 최소화합니다. 다른 API도 인증 검사가 빠진 곳이 없는지 공통 미들웨어(`requireLogin`, `requireRole`)로 통일합니다. 지금은 핸들러마다 `if (!req.session.user)`를 따로 검사합니다.

## 2. 업무 무결성

### 2-1. 🟠 서버 측 예산 초과 검증
- **현황:** 작성 화면에서 예산·지출 누계·잔액을 보여 주지만, 서버에서 상신이나 승인 때 예산 초과를 막거나 경고하는 로직은 찾지 못했습니다.
- **조치:** 상신·최종 승인 API에서 계정과목별 잔액을 다시 계산합니다. 재정부 정책에 따라 **차단**, **경고 후 진행**, **초과 사유 필수 입력** 가운데 하나를 고릅니다. 초과 승인 건은 별도로 표시해 감사에 대비합니다.

### 2-2. 🟡 결재·금액 처리 트랜잭션 점검
- 결재 승인, 일괄결재, 예산편성 반영처럼 여러 테이블을 바꾸는 작업이 모두 트랜잭션으로 묶여 있는지 확인합니다. 일괄결재 도중 일부만 실패했을 때의 처리 기준도 정합니다.

## 3. 품질 · 유지보수

### 3-1. 🟠 자동화 테스트 도입
- **현황:** 서버에는 테스트가 없습니다(`npm test`가 비어 있음). `scratch/`의 임시 스크립트로 수동 확인하고 있습니다. 결재선 순번 공백, 기안자 미등록처럼 한 번 고친 버그가 다시 생기기 쉬운 구조입니다.
- **조치:** 테스트용 DB로 Jest/Vitest + Supertest 통합 테스트를 만듭니다. 우선 범위는 다음과 같습니다.
  - 상신 → 순차 승인 → 최종 완료 / 반려
  - 결재선 순번 공백, 위원장 미등록, 재정부 기안 즉시 완료
  - 권한별 목록 조회, 수정·삭제 권한
  - 예산편성 승인 시 예산·계정 자동 반영과 코드 채번

### 3-2. 🟡 `server.js` 모듈 분리
- **현황:** API 70개 이상이 `server.js` 한 파일(4,554줄, 173KB)에 들어 있습니다. 게시판만 `routes/`로 분리되어 있습니다.
- **조치:** 기능별로 `routes/`(auth, approval, budget, budget-plan, admin, notice)와 `services/`(결재선 탐색, 예산 계산, 알림 발송)로 나눕니다. 테스트(3-1)를 먼저 만든 뒤 단계적으로 옮기면 안전합니다.

### 3-3. 🟡 개발용 코드 정리
- `/api/dummy-claims`, `/api/dummy-claims-bulk`가 운영 API에 함께 있습니다. 화면(`InitialExpenseInput`)에서 실제로 쓰고 있으므로 이름과 용도를 명확히 하고 권한을 재정부·관리자로 제한합니다.
- `MOCK_DATE` 환경변수가 운영에서 실수로 켜지지 않도록 운영 환경에서는 무시하게 합니다.
- `scratch/`, `migrate_*.js`, `migration_*.sql`은 `migrations/` 디렉터리와 버전 관리 도구(예: Knex migrations)로 정리합니다.
- `server.log`, `.DS_Store` 같은 파일이 저장소에 섞이지 않게 `.gitignore`를 보완합니다.

### 3-4. 🟢 PC/모바일 화면 공통화
- **현황:** 화면 23개가 PC용과 모바일용으로 따로 있어서 기능을 바꿀 때마다 두 곳을 고쳐야 합니다. 릴리스 노트에도 "(PC/모바일 공통)" 수정이 반복됩니다.
- **조치:** 데이터 조회·검증 로직을 composable(`useApprovalList`, `useBudgetTree` 등)로 빼서 두 화면이 함께 쓰게 하고, 화면에는 레이아웃만 남깁니다.

## 4. 운영 · 인프라

### 4-1. 🟡 배포 자동화와 버전 관리
- **현황:** `deploy.sh`로 이미지를 빌드·push 하지만 `kubectl set image` 단계는 주석 처리되어 있습니다. k8s 매니페스트의 이미지 태그는 `0.72`(2026-04)에 머물러 있어 실제 운영 버전과 맞지 않을 수 있습니다.
- **조치:** GitHub Actions로 태그 push → 빌드 → 배포 → 롤아웃 확인을 자동화합니다. 매니페스트 버전과 릴리스 노트 버전을 맞춥니다.

### 4-2. 🟡 모니터링 · 로그 · 백업 검증
- `console.log`(30여 곳)와 `server.log` 대신 구조화 로그(pino 등)를 쓰고, 알림톡 발송 실패를 별도로 기록·재시도합니다.
- 헬스체크 엔드포인트와 k8s liveness/readiness probe를 추가합니다.
- 백업은 스크립트로 만들고 있지만 **복구 리허설**을 분기마다 하고 결과를 기록합니다. 업로드 파일(현재 약 106MB)도 같은 주기로 백업합니다.
- MariaDB가 단일 인스턴스이므로 장애 시 복구 목표 시간(RTO)과 허용 데이터 손실 범위(RPO)를 정해 둡니다.
